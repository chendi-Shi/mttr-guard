# 本机真实 HTTP 与监控试点

本试点使用真实 HTTP 请求、Prometheus、Alertmanager、OpenTelemetry 和独立 API/worker 进程。流量和业务故障是人为构造的，运行域为 `LOCAL_LAB`，不能计为生产事故或 MTTR 降幅证据。诊断采用四角色确定性规则基线，不包含 LLM 质量评估。

## 做了什么、怎么做、解决什么问题

| 做了什么 | 怎么做 | 解决什么问题 |
| --- | --- | --- |
| 可重复的隔离服务 | 仅监听 127.0.0.1，独立临时端口、数据库和随机凭据；结束时关闭所属进程 | 不需要企业 staging 即可验证真实接入 |
| 请求产生证据 | checkout 实际调用 inventory，记录同一 trace 的父子 span；计数器和直方图由请求更新 | 避免只验证写死的指标、调用链和发布夹具 |
| 真实告警入口 | Prometheus 抓取并评估规则，Alertmanager 带 receiver 凭据投递 | 验证告警规则、标签范围、鉴权及事件入库能连通 |
| 真实人工判断 | 建议产生后暂停，人工决定是否回退；决策绑定事件和建议哈希 | 避免脚本冒充人工审批，也保留等待时间 |
| 独立恢复验证 | 人工决定后，实验控制器切换版本；只读 worker 检查三个连续健康窗口 | 避免把发布成功响应直接算作业务恢复 |
| 可核对的结果 | 保存计划、发布记录、指标响应、span、事件时间线、审计备份与证据 SHA256 | 保留失败尝试并支持核对结果来源 |

## 环境与运行

完整启动脚本目前支持 Windows AMD64。Python 3.11+，无需 Docker。安装脚本从官方 GitHub release 下载固定版本 Prometheus 3.5.0 / Alertmanager 0.28.1，并按同一 release 的 SHA256 清单校验；这不构成第三方独立供应链签名验证。

在仓库根目录的虚拟环境中运行：

```powershell
python -m pip install -r requirements-local-pilot.txt
python -m scripts.install_local_pilot_tools
python -m scripts.run_local_pilot --output artifacts/local-pilot-my-run
```

每次必须使用新的输出目录。脚本先写入 `plan.json`，再预热、运行现有只读预检、注入故障。预检失败即停止，不生成通过结论。`report.json` 保存状态和失败阶段。

注入前还会用 `baseline-gate.json` 记录基线是否满足已登记的恢复门槛。错误率、P99、样本量、灰度 QPS 或样本年龄在故障前就不合格时停止，避免在原本不健康的环境上制造无法验证的故障。该检查源于 2026-09-29 的实际试点发现；此前失败尝试的原始结果仍保留。

流量目标 40 请求/秒，其中每 20 个请求有一个进入 canary。r41 正常处理折扣；r42 将 `five` 当整数解析，导致实际 HTTP 500。inventory 仍正常。告警条件为 30 秒灰度错误率 >5% 且稳定组错误率 <1%，持续 4 秒。抓取/规则周期均为 2 秒。

恢复条件在故障前固定：三个连续、不重叠的 30 秒窗口，灰度/稳定组错误率 <1%、P99 <500ms、灰度/对照样本均 ≥20、灰度 QPS ≥基线 2 的 50%、样本年龄 ≤5 秒、目标版本 r41 生效、下游健康；相邻观察间隔不得超过 45 秒。

## 人工处置

出现 `AWAITING_OPERATOR` 后，读取输出目录的 `diagnosis.json`、`fault-prometheus.json`、`fault-evidence.json` 和发布记录，核对灰度/稳定组差异、失败 span、版本和回退兼容性。此步骤需要实际操作者判断；等待超时不会自动接受建议。

操作者接受时，在该目录原子写入 `decision.json`，内容包括以下字段（事件 ID 和哈希必须来自当次输出）：

```json
{
  "action": "rollback",
  "incident_id": "当次事件 ID",
  "plan_hash": "当次建议 hash",
  "actor": "实际操作者标识",
  "recorded_at": 0,
  "reason": "人工核对后填写的处置依据"
}
```

`recorded_at` 使用实际 Unix 时间。可先写 `.partial` 文件再重命名，避免读到半份 JSON。选择拒绝时可写 `action: stop` 并保留判断依据；脚本停止并报告未完成。等待上限 240 秒，同时不超过建议有效期。迟到的判断需重新取证，不能修改旧报告冒充完成。

实验控制器按人工决定使用独立控制凭据切换本机服务版本，随后调用工作流的人工处置记录入口。API/诊断/观察进程不持有发布控制凭据；取证子进程只继承只读证据凭据。该路径不连接企业发布平台，不能证明企业审批或回滚系统已集成。

## 证据与边界

输出目录全部在忽略的 `artifacts/` 下，包含实验密钥、令牌、数据库及本机路径，**不要整体上传**。可发布经过检查的摘要、时间线和哈希；审计备份的密钥单独在本机保留。哈希用于确认文件一致性，不能独立证明采集方可信或数据没有在生成前被修改。

实时高频 span 写入和监控存储位于系统临时目录，以减轻同步工作目录的 I/O 干扰。测试服务使用控制凭据有序停止，写完 span 后复制到忽略的试点目录；查询响应、发布记录、审计库和报告也留在该目录。Prometheus/Alertmanager 的临时数据库不长期保留，后续只能核对试点期间保存的查询响应和文件哈希。

报告分别记录告警时间、入库、证据就绪、建议生成、人工判断、回退和恢复确认。人工等待包含聊天与工具调度，不能作为纯人工操作耗时。无对照组时只报告该次流程耗时，不宣称降低 MTTR。停止、超时和失败尝试都需保留；一次通过不代表成功率或生产准入。

`inventory` 是同一测试进程中的独立 HTTP 请求处理器；没有跨主机网络、真实数据库迁移、企业 IAM、多机调度、生产负载或不可变审计存储。本轮优先跑通一次闭环；后续再登记 10–20 次包含下游失败、证据缺失、重复告警和 worker 重启的演练，避免先看到结果再改变成功标准。

CI 运行真实 HTTP 故障、trace 关联、只读凭据拒绝写入和版本前置条件测试，不替代带人工决策的完整试点。

## 本次接入发现的兼容性问题

真实 Prometheus 3.5.0 将数值查询时间四舍五入到毫秒（[官方实现 parseTime](https://github.com/prometheus/prometheus/blob/v3.5.0/web/api/v1/api.go#L1917)）。原采集器直接发送更细精度的时间，再拒绝任何未来时间，导致合法响应偶发被拒绝。采集器现在用十进制定点向下对齐查询时间，保留严格的未来数据和 15 秒过期校验，也保留独立的底层样本年龄检查。新增测试覆盖向上舍入边界和真正的未来数据。

本机服务也修正了 HTTP 头大小写造成的 trace 断链：提取上下文前统一头名称，并用真实嵌套请求验证 trace ID 和父 span ID。连接队列扩至 128，以容纳并发 checkout 请求及其内部 inventory 请求；这不是容量保证，报告仍使用实际请求量。
