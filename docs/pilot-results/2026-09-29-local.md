# 2026-09-29 本机故障试点续测

**结果：已真实执行本机回退，但没有通过恢复确认。** 同一已知故障场景共运行 7 次独立接入尝试，其中 6 次注入了 r42 灰度错误，3 次根据用户明确的回退指令从 r42 切回 r41。回退后错误率为 0%，但最多只有连续 2 个符合预设标准的 30 秒窗口；最终均未达到 3 个。第 7 次在注入前预检失败。没有完成可计量的全流程 TTR，更没有 MTTR 降幅或生产准入结论。

[机器可读逐次记录、指标、审计状态与文件哈希](2026-09-29-local.json)保留每次失败。原始 Prometheus 响应、span、发布记录、数据库和密钥保存在本机忽略目录 `artifacts/local-pilot-20260929-*`，不上传到 GitHub。

## 做了什么、怎么做、解决什么问题

| 做了什么 | 怎么做 | 解决什么问题 |
| --- | --- | --- |
| 执行用户指定的本机回退 | 用户对 r42 → r41 表示同意后，旧建议过期；每次重新预检并核对相同服务范围、5% 灰度、版本、错误率、健康稳定组、失败 span、下游和新建议哈希，再使用单独的实验控制凭据切换版本 | 避免拿过期建议操作，同时验证人工指令、处置记录和真实版本变化能接通 |
| 坚持独立恢复判定 | 回退后只读取实际 Prometheus 指标和请求产生的 span；三个不重叠的 30 秒窗口均须满足故障前固定门槛 | 防止看到版本号或一次正常响应就宣布恢复 |
| 减少本机采集干扰 | 高频 span 由后台批量写入系统临时目录，测试服务有序停止并刷盘；Prometheus/Alertmanager 的运行存储也转到临时目录 | 降低同步文件夹的高频 I/O 对测试流量的干扰 |
| 校准流量发生器 | 先后试验 8、20、12 个错峰线程，目标始终是约 40 请求/秒、5% 灰度；逐次保留实测 QPS/P99 | 识别发压不足与过载导致的不同失败原因，不以目标值代替实测值 |
| 新增基线健康门 | 注入前对现有预检结果再检查错误率、P99、QPS、样本量与新鲜度是否满足已登记恢复标准，记录 `baseline-gate.json` | 避免故障前已不满足恢复要求，却继续故障注入和产出不可达的恢复目标 |

## 固定故障和判定标准

本机 checkout 服务以真实 HTTP 请求调用本机 inventory。r42 将合法折扣字符串解析为整数时发生 ValueError，灰度请求返回 HTTP 500；稳定组保留 r41。Prometheus 每 2 秒抓取和评估，Alertmanager 将灰度 30 秒错误率 >5%、稳定组 <1% 持续 4 秒的告警投递到独立 API；诊断、反证与恢复观察由独立 worker 运行。四个分析角色是确定性规则基线，没有使用 LLM。

恢复标准延续 [前一天登记的计划](2026-09-28-local.md)：三个连续、不重叠的 30 秒窗口；灰度和稳定组错误率 <1%、灰度 P99 <500ms、两组样本各 ≥20、灰度 QPS ≥1、样本年龄 ≤5 秒、r41 生效且下游健康。观察到期进入 `NEEDS_ATTENTION`，不得登记 `RECOVERED`。

## 七次尝试的实际结果

| 次序 | 灰度基线 QPS / P99 | 注入 / 回退 | 结果 |
| --- | ---: | --- | --- |
| 01 | 0.964 / 477.5ms | 注入；未回退 | 告警、建议已产生；用户回复到达时建议及等待期限已过，试点已停止 |
| 02 | 0.714 / 900ms | 注入；未回退 | 诊断发现灰度 QPS 不足，转人工关注 |
| 03 | 0.678 / 968.3ms | 注入；未回退 | 诊断发现 30 秒样本不足，转人工关注 |
| 04 | 0.929 / 870ms | 注入并回退 | 错误率归零；最多连续 2 个健康窗口，随后 QPS/P99 不合格，最终 `NEEDS_ATTENTION` |
| 05 | 1.214 / 247.9ms | 注入并回退 | 错误率归零；最多连续 2 个健康窗口，随后 QPS/P99 波动，最终 `NEEDS_ATTENTION` |
| 06 | 1.714 / 760ms | 注入并回退 | 请求量增加，但基线及所有恢复窗口的 P99 超过 500ms，最终 `NEEDS_ATTENTION` |
| 07 | 0.643 / 987.1ms | 无注入 | 只读预检样本不足，注入前停止 |

这些是同一天对同一已知故障、不同本机流量和存储设置的探索性尝试，**不是 7 个独立事故或成功率研究**。04–06 的发布记录均为 r41 → r42 → r41；各自的 HMAC 审计历史经离线校验，分别有 167、164、161 条记录；结束时没有待处理任务。01–06 的故障请求与失败 span、07 的停止阶段以及每次文件哈希见机器可读记录。

用户的回退指令是在 01 的建议到期后给出的。04–06 将这条指令用于同一故障场景，每次都重新核对新证据并绑定新的建议哈希。**用户没有在每条新建议生成之后再次作判断**，所以不能把这三次记录解释为三次独立的实时人工决策，也不能从自动记录时间计算人工判断耗时。

诊断从告警 `startsAt` 到生成建议，在 01/04/05/06 分别约为 1.884/3.167/3.069/2.453 秒。`startsAt` 不等于注入时刻。由于没有一次得到三个健康窗口，恢复时间为空；所有“MTTR 改善”字段应视为未评估。

## 发现与下一步

试点证实真实告警、只读取证、同故障回退建议、人工指令绑定、实际本机版本切换和持续观察可以连接；也证实守门逻辑在 QPS、样本不足、延迟或连续窗口不达标时拒绝确认恢复。本机服务、采集器和同步工作目录之间的负载波动使恢复结果不稳定。后台写入改善了 05 的基线表现，20 个线程在 06 增加 QPS 同时推高 P99；07 在注入前被样本门槛拦下。不能从这些观察确定单一瓶颈或生产容量。

下次应使用有固定性能余量、非同步工作盘的专用测试主机或可控 staging，先登记并核实无故障基线持续满足原标准，再安排值班人员在线完成一次**新建议生成后的现场判断**，最后验证三个健康窗口。完成这一条闭环后再开展预登记的 10–20 次不同故障演练及对照评估。本机结果不能代表字节等大型企业的生产环境。

本机最终完整回归 211 项通过，75.851 秒；增量服务测试覆盖真实故障、跨 HTTP trace 父子关联及只读凭据拒绝发布、停止操作。试点本身是探索性验证，不能用单元测试通过替代失败的恢复验收。
