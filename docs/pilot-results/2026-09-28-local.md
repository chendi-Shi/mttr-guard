## 做了什么、怎么做、解决什么问题

| 做了什么 | 怎么做 | 解决什么问题 |
| --- | --- | --- |
| 接通真实监控链路 | 独立 Prometheus 抓取 HTTP 请求指标，Alertmanager 投递到独立 API，worker 只读取证 | 从内置模拟器验证推进到真实外部进程接入验证 |
| 修复 Prometheus 时间精度缺陷 | 查询时间向下对齐毫秒，保留过期和未来数据拒绝规则，新增两项回归测试 | 合法响应不再因毫秒四舍五入被误判为未来数据 |
| 修复实验服务 trace 断链 | HTTP 头名称标准化，实际嵌套请求断言相同 trace 与正确父 span | 指标异常能够关联到实际失败请求和调用环节 |
| 固定计划并保留失败 | 故障前记录范围、告警阈值、恢复标准；每次使用新目录，保存失败阶段和文件哈希 | 避免只挑成功结果，也避免事后降低恢复标准 |
| 保留真实人工环节 | 生成建议后等待操作者判断，超时停止所属进程 | 避免将自动脚本审批冒充人工处置证据 |

## 环境与预先固定的标准

- Windows AMD64 / Python 3.14.7；Prometheus 3.5.0、Alertmanager 0.28.1 官方发行包经过 SHA256 清单核对；OpenTelemetry SDK 1.36.0、prometheus-client 0.22.1。
- 服务 checkout，scope 为 `local-lab / local-pilot / loopback / experiment / checkout`；仅监听本机，所有业务请求是合成测试流量。
- 目标 40 请求/秒，每 20 个请求中的一个进入灰度。r41 正常，r42 参数解析产生实际 ValueError 和 HTTP 500；inventory 仍健康。实际流量低于目标，报告使用实测数值，不宣称达到容量目标。
- 30 秒灰度错误率 >5% 且稳定组 <1%，持续 4 秒触发告警。抓取与规则评估周期 2 秒。
- 恢复需三个连续 30 秒健康窗口：灰度/稳定组错误率 <1%、P99 <500ms、两组样本分别 ≥20、灰度 QPS ≥1、样本年龄 ≤5 秒、目标 r41 生效、下游健康。**本次没有执行恢复验证。**
- 四角色采用确定性规则基线，未调用 LLM；不存在真实模型质量或自主推理能力的试验结果。

## 实际观测

预检：灰度/稳定组错误率均 0；灰度 QPS 1.429，30 秒灰度样本约 42.86，稳定组约 826.07，P99 450ms，样本年龄 2.065 秒，trace 样本 43。Prometheus `increase` 使用外推，样本值可以是小数；它与实际 HTTP 整数计数的含义不同。

建议时：灰度错误率 **29.01%**，稳定组 **0%**；灰度 QPS 1.560，灰度样本约 46.79，稳定组约 893.67，P99 445ms，样本年龄 1.726 秒。变更证据指向 r41 → r42 的 5% 灰度；trace 失败点 `checkout.validate`，下游健康。四角色均引用本次证据 ID，建议回退到 r41，与预先注入的故障一致。该故障是已知、非盲测场景，不能据此报告诊断准确率。

| 阶段 | 实测耗时 |
| --- | ---: |
| 告警 `startsAt` → API 接收 | 1.123 秒 |
| API 接收 → 证据就绪 | 1.667 秒 |
| API 接收 → 建议生成 | 2.130 秒 |
| 告警 `startsAt` → 建议生成 | 3.253 秒 |
| 等待人工判断 | 上限 240 秒后退出，包含轮询调度误差 |
| 人工实际操作耗时 | 未测得；没有收到决策 |
| 回退 → 恢复确认 / 全流程 TTR | 无结果 |

告警起点使用 Alertmanager 转发的 `startsAt`，不等同于故障注入时刻。机器可读报告保留完整时间戳与注入时间，不能将上表 3.253 秒当作 MTTR。

试点共完成 **6,907 次 checkout 请求**：稳定组 6,562 次 HTTP 200；灰度 64 次 HTTP 200、281 次 HTTP 500。保存 **20,721 条 span**，281 条失败的 validate span 均有同 trace 的父请求 span。发布记录只有启动 r41 和注入 r42，**没有 r41 回退记录**。

停止后离线核验：1 个事件仍处于 `RECOMMENDED`，14 条 HMAC 审计记录通过，0 个待处理任务；已生成可校验备份。HMAC 密钥由本机持有，这不是企业不可变审计存储或独立第三方证明。
