# 2026-09-29 本机真实 HTTP 故障试点：完成一次恢复闭环

**结果：一次隔离本机试点达到预先固定的恢复标准。** 真实 HTTP 灰度故障触发 Prometheus/Alertmanager 告警，系统读取指标、发布记录和 OpenTelemetry 调用链，生成 r42 → r41 建议；根据用户此前对**同一故障场景**的明确回退指令，重新核对本次证据与新建议后执行本机回退。独立观察 worker 随后记录三个连续、互不重叠的 30 秒健康窗口，事件进入 `RECOVERED`。这证明此配置下的技术流程可连通，**不是生产准入或 MTTR 降幅证据**。

[机器可读摘要、时间线、指标、审计结果及原始文件 SHA256](2026-09-29-http-reuse.json)。原始监控响应、span、数据库和实验凭据只保存在本机忽略目录 `artifacts/local-pilot-20260929-08`，不上传 GitHub。此前七次失败/未完成尝试仍见[探索性续测报告](2026-09-29-local.md)，没有从记录中删除。

## 做了什么、怎么做、解决什么问题

| 做了什么 | 怎么做 | 解决什么问题 |
| --- | --- | --- |
| 修复本机负载发生器的连接开销 | 12 个错峰 HTTP worker 各自复用 checkout 连接；checkout 处理器也复用到 inventory 的 HTTP 连接，完整读取响应并在连接异常后重建 | 先前频繁创建 TCP 连接使实际灰度 QPS/P99 在故障前或恢复期达不到固定门槛，无法判断业务是否真正恢复 |
| 保留真实请求和调用链 | 仍由 checkout 实际请求 inventory；HTTP 500、Prometheus 指标、trace 父子关系都来自处理过的请求 | 避免用静态夹具或直接改指标制造通过结果 |
| 按固定门槛验收恢复 | 注入前 `baseline-gate.json` 全部通过；回退后三个 30 秒窗口均检查错误率、样本、QPS、P99、数据新鲜度、r41 和下游状态 | 防止只看到版本切回或单次请求正常就误报 `RECOVERED` |
| 核对完整性和残留任务 | 逐文件校验 11 个原始工件 SHA256，并用本机密钥离线校验 82 条 HMAC 审计记录；完成时待处理任务为 0 | 让时间线、发布动作和恢复状态可回查，发现丢失或改动的本机证据 |

## 证据范围与下一步

这是一项同一台 Windows 主机上的单例 `LOCAL_LAB` 试验，业务流量和故障均为人为构造，四个分析角色使用确定性规则，没有评测 LLM。用户的“退吧，”是在早前同一 r42 → r41 场景提出的；本次在新告警后重新确认范围、版本、指标、trace、建议哈希及有效期，但**用户没有在本次新建议出来后再次实时判断**。因此约 32.5 秒的记录等待包含聊天和工具调度，不能算人工判断耗时。实验控制器有单独本机控制凭据，不能证明企业发布平台已接入。

本次证明了**技术闭环一次成功**，尚未证明重复成功率、其他故障下的安全性、企业环境容量/高可用、生产可用性或因果 MTTR 改善。下一步应预登记 10–20 次含下游故障、证据缺失、重复告警及 worker 重启的演练，安排值班人员在新建议出现后现场判断；随后在可控 staging 与现有流程做对照。没有对照组前，只报告流程表现，不报告“降低 MTTR 百分比”。
