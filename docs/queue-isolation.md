# v0.6：多服务队列隔离与公平调度

## 本轮做了什么、怎么做、解决什么问题

| 做了什么 | 怎么做 | 解决的问题 |
|---|---|---|
| 按服务、按队列限制积压 | 使用完整五维 scope，分别统计 diagnose/observe 的 READY 和 RUNNING 任务；在入库事务中检查服务额度及全局 1000 上限 | 过去单个服务可占满全局队列；现在默认每类最多 100 个，不再由单个服务的诊断告警占满全部额度 |
| 同类队列在服务间轮流调度 | 新增持久化 `pilot_dispatch`，记录每个 scope/kind 最后被调度的递增序号；优先选择最久没有获得调度的合格服务，再按服务内 due 和入库顺序选择任务 | 过去服务 A 的旧积压会排在服务 B 新事故前；现在 B 不必等 A 的积压全部清空 |
| 多 worker 共用服务并发上限 | 在 `BEGIN IMMEDIATE` 中统计该 scope/kind 尚未过期的 RUNNING 租约，检查上限后再分配新租约 | 过去扩容 worker 可能同时冲击同一个监控源或模型入口；现在每服务、每类队列默认最多两个有效执行租约 |
| 人工操作也遵循容量控制 | refresh/observe 在原有鉴权、request ID 幂等事务内检查容量；拒绝时不消费 request ID、不改变事件状态 | 避免人工重试绕过队列额度，同时允许容量释放后重用原 request ID 重试 |
| 拒绝有明确响应，容量可观察 | enterprise API 返回 503、`code=queue_full`、`Retry-After: 5`；运行接口和 Prometheus 输出当前额度及有效租约数 | 告警发送方能识别临时拒绝，值班人员能区分容量占用与过期租约 |

## 配置

每个服务的配置可增加：

```json
"queue_limits": {
  "max_pending_per_queue": 100,
  "max_running_per_queue": 2
}
```

未填写时使用以上默认值。积压上限须为 1–1000 的整数，执行租约上限须为 1–32 的整数，且不能大于积压上限。拒绝布尔、浮点、未知字段和非法范围。设置积压上限为 1 时也应显式设置执行上限为 1。

`max_pending_per_queue` 包含 READY（含尚未到期的重试）和 RUNNING（含过期但尚未回收的租约）。DONE 不占额度。diagnose 与 observe 分别计数，不共用服务额度，但仍共同受全局 1000 个活跃任务的总上限约束；这不是为每个服务预留独占容量。

当额度已满时，重复告警仍返回已存在的 incident ID，不会再占一个名额。含多个告警的请求若有任何新增项超额，整个批次回滚，不会部分入库后返回失败。发送方必须持久保留待投递告警，并在收到临时拒绝后使用带退避/抖动的重试；系统没有替发送方保存被拒绝的新告警。

API 和 worker 沿用每次操作读取配置的机制。调整队列额度不改变取证范围、PromQL 或恢复策略，也不改变 `collection_hash`，不会把既有事件误判为证据配置漂移。调低额度不会取消已经运行的任务、删除积压或强制释放租约；只会阻止继续超额入队/领取，直至占用下降。

所有 worker 必须使用一致的配置。若不同进程采用不同并发上限，较宽松的进程仍可能按自己的配置领取；本版本没有跨主机的集中策略分发。

## 调度规则与具体例子

假设 diagnose 队列中已有 A1、A2、A3，随后进入 B1、B2、B3；各自 due 相同，租约有空位且任务执行后释放。在本轮调度器中，领取顺序为 A1、B1、A2、B2、A3、B3，而非先排空 A。服务内按 due 排序，再按事件入库顺序稳定排序。

调度序号不依赖墙上时钟，并与领取租约及 JOB_STARTED 审计处于同一事务；写入失败一同回滚。worker 重启或备份恢复后仍保留该顺序。因耗尽诊断次数或观察超时而被终止的任务也占一个调度轮次，避免同一服务的失败积压独占维护处理。

已达有效租约上限的服务暂时被跳过，其他有空位且任务到期的服务仍可获调度。过期租约不占执行额度，重新领取后仍使用新 lease token，旧结果不能写回。该上限约束的是有效租约，不是网络端实际活跃请求数；旧进程暂停、租约到期但尚未终止时，物理请求可能重叠。现有独立子进程 70 秒期限和 120 秒默认租约继续适用，仍需要监控资源和子进程状态。

diagnose/observe 的轮流调度互相独立。`--queue all` 仍优先观察任务，因此不能承诺在持续观察压力下诊断不会等待；持续部署应继续使用独立的 diagnose 和 observe worker 进程。轮次公平不代表耗时公平，也不提供加权优先级或截止时间 SLO。

## 查看与定位

认证后的 `/api/operations` 新增 `queue_limits`，其 `jobs` 项新增 `active_leases`。`/metrics` 新增：

- `mttr_guard_queue_pending_limit{kind="diagnose|observe"}`：当前服务、当前配置的积压上限。
- `mttr_guard_queue_running_limit{kind="diagnose|observe"}`：当前服务的有效执行租约上限。
- `mttr_guard_active_leases{kind="...",state="..."}`：当前有效租约数；READY 及过期 RUNNING 租约贡献 0。

所有队列占用和额度只针对认证身份绑定的服务返回；服务名不作为由请求任意注入的标签。多服务抓取须在 Prometheus target labels 中保留服务标识，并使用各自的 viewer 身份。原有 `mttr_guard_jobs` 仍报告包含过期租约的积压总数，两者应结合查看。

如果收到 503，先检查当前服务的积压/有效租约和全局部署状态，再核对 worker 健康、采集速度和观察窗口。容量满不代表事件已经恢复；不要通过删除事件或人工修改任务表腾空间。常规人工处置仍使用现有发布平台，平台额度不得阻止值班人员在外部响应事故。

旧 `pilot demo/serve` 入口也使用相同存储容量与调度规则；新版 `queue_full` 错误码、Retry-After 和容量指标属于 enterprise ASGI 入口。

## 升级、验证与边界

升级时自动增加调度元数据表 `pilot_dispatch`，不重写已有事件或审计链，不需要人工搬迁数据。应先做可验证备份，再更新全部 API/worker。旧 worker 不执行新限制，混合版本运行不能保证这些规则。调度表与现有租约一样不在 HMAC 签名保护范围内，不能抵御可直接修改调度元数据的数据库管理员。

新增测试覆盖：服务洪峰隔离、原子批次、重复投递、全局上限、服务内排序与跨服务轮次、观察/诊断额度隔离、并发实例与真实子进程竞争、配置热调整、旧租约隔离、人工操作幂等、调度写入回滚、旧库自动建表、备份恢复和 HTTP/指标作用域。完整命令为 `python -m unittest discover -s tests -v`，专项为 `python -m unittest discover -s tests -p test_queue_isolation.py -v`。

该版本依然使用单机 SQLite，事务和全链审计仍会随历史增长增加耗时。这次提供服务间的调度和容量控制，没有提供 PostgreSQL、多机高可用、完整的 CPU/内存/模型 token 配额或生产吞吐保证。默认额度是可配置的起点，实际值必须由目标环境测试决定；测试中的故障与服务数据为合成输入，不能据此宣称真实 MTTR 降幅。
