# v0.4.1：运行时审计完整性与故障处置

## 修复的实际问题

v0.4 的启动及离线检查可以识别数据库被篡改，但在线操作直接读取 incident JSON 再保存、签名。复现路径是：通过独立 SQLite 连接修改事件摘要；离线检查失败；合法操作者执行 `ack`；保存后的最新 STATE 记录为被篡改的摘要背书，离线检查转为通过。同样的信任缺口存在于后台任务保存结果的路径。

v0.4.1 将完整性校验放入 `PilotStore.tx()`。先执行 `BEGIN IMMEDIATE`，再验证密钥标识、审计链、链头、工作流事件、最新 incident 状态和作用域/状态查询字段，最后才允许业务代码读取或修改数据库。校验和业务操作使用同一连接、同一事务；其他正常 SQLite 写入连接不能插入校验到保存之间。所有现有读取和写入路径共用该入口，包括列表、指标、告警去重、worker 租约获取/完成/失败、人工操作和访问审计。

这不是宿主机防入侵机制。拥有进程代码执行能力、签名密钥或绕过 SQLite 锁直接改写文件的攻击者不在该事务隔离保证内。没有密钥的开发模式只有哈希校验，不能提供对抗恶意重签的保证；持续试点必须使用要求固定审计密钥的 `enterprise` 入口。

## 运行行为

- 完好的既有 v0.4 审计库无需迁移；构造存储实例时先验证。损坏的库拒绝启动，不会自动重签或导入为可信历史。
- 检测失败时回滚当前事务，在该进程内锁定隔离状态，输出不含事件内容或密钥的 `audit_integrity_failed` 严重日志。后续调用直接拒绝，单纯改回数据库内容不会让该进程自动恢复。
- ASGI 的数据接口、`/healthz`、`/readyz` 返回 HTTP 503 和固定错误码 `audit_integrity_failed`。访问审计也不能追加到损坏的链；故障信号由受监督的进程日志及探针返回，不能依赖这条链记录自身故障。静态工作台文件仍可加载。
- worker 在下一个事务边界发现问题后等待停止信号，不继续取证、保存结果或循环重试。已发出的只读采集可能执行到原有期限，但其结果不能写回受损存储。三个进程各自检测，不能据此声称瞬时全局停止。
- 存储完整性失败和普通 SQLite 锁竞争不同：前者需要人工恢复；后者仍保留原有重试行为。告警投递返回 503 时，发送方应保留重试，不能当作持久化接收成功。

## 值班处置

1. 在入口暂停向该实例转发流量，保留发送方重试队列；停止 API、diagnose worker 和 observe worker。按团队流程保留宿主机日志、配置版本、数据库及存在的 journal/WAL 文件，收紧现场访问权限。
2. 使用原审计密钥对保留副本运行 `python -m mttr_guard.enterprise audit-verify --db PATH`。如持有独立保存的可信链头，增加 `--checkpoint checkpoint.json`。不要删除失败的记录、修改链头、换钥或运行重签脚本来清除故障。
3. 选择已验证的备份数据库和对应 `.db.json` 清单，核对来源及独立外部检查点。若备份早于检查点，验证失败是预期的数据缺口信号，需要记录丢失范围和 RPO，不能把回退冒充为完整恢复。
4. 用 `python -m mttr_guard.enterprise restore --db BACKUP --output NEW_PATH` 还原到新路径，独立验签并核对事件。原故障库继续保留。备份还原命令只重置只读任务租约，不执行真实发布操作。
5. 将三个进程全部切换到已验证的新路径，重新启动。确认 `/readyz` 就绪，再恢复入口并投递受控测试告警，检查去重、取证、人工记录及恢复窗口。调查并封堵原始写入来源；单纯重启不是根因修复。

若数据库及密钥的运行环境本身已失陷，需要团队现有的主机恢复与密钥事件流程，不能只依靠本项目恢复命令。项目没有自动发送通知或自动异地保存审计检查点。

## 容量成本与未覆盖范围

当前实现每个事务重放全部历史。成本随审计记录、工作流事件及事件状态大小增长，验证期间持有 SQLite 写锁；多个 API/worker 会互相等待。单次 HTTP 请求可能经过多个事务。不能通过缓存同一数据库里的 `audit_head` 来跳过校验，因为攻击者可以保留链头、仅篡改 incident 内容。

可复现的合成基准：

```powershell
python -m scripts.benchmark_audit_guard --records 1000 10000 --samples 10 --output artifacts/audit-cost.json
```

2026-09-18，Windows 11 / Python 3.14.7，单进程、100 个合成事件；测量 `operational` 查询及追加一条访问审计，共两个受保护事务：

| 起始审计记录数 | 样本数 | P50 | P95 |
| --- | --- | --- | --- |
| 1,000 | 10 | 83.396 ms | 95.799 ms |
| 10,000 | 10 | 494.975 ms | 840.184 ms |

这些结果仅量化本机审计开销，不包含 HTTP、真实采集、模型、并发锁竞争或长时间运行；10 个样本的 P95 即最大观测值。没有据此承诺 QPS/SLO，也没有证明大流量准入。上线前必须在目标硬件、预期历史规模及并发下测量入库延迟和恢复观察缺窗；增长到不能满足目标时，应停止扩大试点，设计独立受保护审计存储、可验证状态索引和历史归档，再验证其一致性与故障恢复。不能直接截断链释放容量。

签名覆盖工作流事件、最新事件 JSON 及其 id/scope/state 查询一致性。告警 dedup 查询列、请求去重表、worker 心跳和任务租约等调度元数据没有完整签名覆盖。完整数据库被替换为旧的合法快照，仍需要独立可信检查点才能发现；同时持有数据库与密钥的人仍能重签。这次修复解决运行中篡改被正常业务操作掩盖的问题，没有把本地 HMAC 链变成不可篡改存储或多机高可用系统。

## 回归与演练

`tests/test_integrity.py` 覆盖原始重签漏洞、多个已运行实例的读写入口、损坏链头/JSON/事件/签名、旧状态重放、采集中篡改、隔离等待、恢复后必须重启以及竞争写入不能穿过校验事务。ASGI 测试确认探针、数据接口、告警及人工操作返回 503、不泄露被篡改内容、不推进审计链。

`python -m scripts.run_enterprise_drill` 还会在 API 和两个真实 worker 子进程运行时篡改临时 DEMO 库，验证拒绝读写且数据库内容保持不变。该步骤接在正常恢复、备份和还原之后；CI 的 Linux/Windows × Python 3.11/3.14 矩阵自动执行它。实际验证结果见 [验证记录](validation.md)。
