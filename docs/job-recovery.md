# v0.5.1：任务退出与人工接续

## 解决的问题

此前，诊断采集返回异常会在第三次尝试后转为人工处理，但 worker 在领取任务后被强制终止时，没有机会执行异常处理。租约到期后可以反复领取同一任务，持续消耗监控与模型资源。观察任务也可能在停机重启后，先发起已经超过观察期限的采集，再判定超时。

现在，领取任务前就在审计保护的数据库事务内检查尝试预算和观察期限；到达退出条件时不调用证据源或模型。

## 明确的运行规则

| 场景 | 行为 |
|---|---|
| 诊断采集失败或进程在领取后退出 | 每次成功领取均消耗一次尝试；同一轮诊断最多三次，报错与崩溃共享预算 |
| 第三次诊断仍持有有效租约 | 不提前终止；允许在租约内正常返回结果 |
| 第三次诊断遗留租约到期 | 下一次领取检查将事件置为 `NEEDS_ATTENTION`、任务置为 `DONE`，不开始第四次采集 |
| 第三次诊断明确返回异常 | 立即转为人工处理，保存异常类型，不保存可能含凭据的异常正文 |
| 观察任务已过期限 | 到期后不发起新采集；已在执行的采集在期限处或之后返回，也不新增恢复窗口或宣告恢复 |
| 已终止任务的旧 worker 返回 | 租约失效，旧结果与旧失败回调均不能覆盖人工处理状态 |
| 多个 worker 同时重启 | SQLite 事务串行决定终止，只产生一条该轮 `JOB_STOPPED` 记录 |
| 备份还原 | 保留已经消耗的次数；重置运行租约不会自动给予新的诊断预算 |
| 值班人员重新收集证据 | 复用现有 operator 操作、服务权限、说明和 request ID 幂等约束，开启一轮新的三次预算 |

恢复观察的次数不套用诊断三次上限，仍以事件冻结的 `observation_deadline` 为总期限。正常健康窗口会重置观察任务的尝试计数。终止观察会清零健康连续次数，并保留此前的观察历史；不会把超时事件统计成已恢复。

终止事件状态、任务状态、租约撤销、错误类型和审计写入处于同一事务。任何写入失败都会整体回滚，下次轮询重新处理。每次 `claim()` 最多处理一个任务；终止后返回空结果，持续 worker 最多等待通常的一秒轮询间隔后再处理下一项，避免在一个事务中清理整个积压队列。

## 值班人员如何接续

1. 在工作台打开“需要人工处理”的事件，核对处理原因、证据和时间线中的 `JOB_STOPPED` / `COLLECTION_FAILED`。
2. 检查 worker 退出原因、资源限制、采集网关可用性和配置。错误正文不会进入事件审计，供应方日志须在相应系统按权限查看。
3. 修复原因后填写处理说明，点击“重新收集证据”。新诊断会重新采集和生成建议，旧建议审批不会被沿用。
4. 若已经在现有发布平台完成人工处置，可填写预期运行版本并重新开始恢复观察。它建立新的观察期限，不执行发布操作。

查看者只有读取权限，不能重新排队。重复提交同一个操作 request ID 不会再清零已消耗次数或夺走当前 worker 的租约。系统不会自动向值班人员发消息；交接和通知继续使用团队已有渠道。

## 监控与部署

`GET /api/operations` 新增 `needs_attention` 字段；`GET /metrics` 新增 `mttr_guard_needs_attention` gauge，均按认证身份绑定的服务隔离。此数值包含所有 `NEEDS_ATTENTION` 事件，例如证据冲突、人工拒绝、暂停观察、采集失败和超时；它不是“worker 崩溃次数”。重新收集证据或重新开始观察后，事件离开该状态，数值下降。

`deploy/alerts.yml` 增加连续两分钟有人工待处理事件的规则草案。需由团队加载到实际监控系统并配置路由；提交规则文件本身不会发出通知。多服务抓取应在 Prometheus target labels 中保留服务标识，并各自使用相应服务的 viewer 身份。

没有新增表或依赖，正常 v0.4/v0.5 审计库可直接打开。建议在同一次维护中更新 API、诊断 worker 和观察 worker；旧 worker 代码仍可能继续领取任务，只有全部领取方升级后才能保证新预算规则。升级前先按现有手册保留可验证备份。

## 验证与边界

`python -m unittest discover -s tests -p test_job_recovery.py -v` 覆盖共享预算、真实子进程突然退出、有效租约保护、旧结果隔离、并发重启、原子回滚、备份还原、人工重试幂等、观察期限和指标作用域。完整测试还验证 HTTP 查看者拒绝操作、operator 重试及 Prometheus 指标变化。

测试中的子进程与 SQLite 事务是真实的，时间由测试时钟推进，输入为合成数据。该验证不代表生产 MTTR 或真实容量。仍使用单机 SQLite；内部调度表不在 HMAC 签名保护范围内，此预算机制面向进程/采集失败，不抵御能直接篡改任务计数的数据库管理员。

worker 全部停机时不会自动更新事件状态；启动后在任务可领取时执行退出检查。有效租约不会被提前抢占，因此观察期限先于租约到期时，需等待旧结果返回或租约到期后完成状态更新。`mttr_guard_ready` 和已有 worker 缺失告警仍需一起监控，不能用人工待处理数量代替 worker 存活检查。
