# v0.4.2：有预算的已验证记录缓存

## 改进目标

v0.4.1 修复了正常请求掩盖数据库篡改的问题，但每次查询、心跳和人工操作都重新解码全部审计 JSON、计算 HMAC 和状态摘要。访问历史增长后，即使没有任何旧记录变化，这些计算也会重复。

v0.4.2 保留同一事务内的全量扫描和完整性判断，只缓存之前通过整体验证的 SQL 字段原文及其校验结果。没有新增数据库表、修改签名格式或迁移历史；备份、还原和独立 `audit-verify` 默认仍不使用缓存。

## 校验边界

1. 取得 `BEGIN IMMEDIATE` 事务锁后，重新读取密钥标识及全部有序审计记录。序号连续性、前驱链接、当前链头和外部检查点每次都检查。
2. 对每行比较其字段与该进程上次验证成功的副本，包括原始 payload、前驱、签名及字段类型。浮点表示也须一致，防止 Python 将 `1`/`1.0` 或正负零视为相等、但 JSON 摘要不同的情况。完全相同才复用已验证结果；新增或修改的行重新解码并验签。不能只比较 seq 或链头。
3. 从本次扫描构建最新状态摘要和工作流引用。每个引用的实际事件、最新 incident body/scope/state 都重新从当前事务读取；原文不同或不在缓存时重新计算摘要。仍比较引用和实际摘要，仍检查额外/缺失的事件和状态。
4. 缓存绑定审计密钥标识，保留的数据只有原文及不可变的摘要/引用元组，不保留完整的解码 JSON 树。缓存只存在于进程内，不从数据库或备份加载“可信缓存”。
5. 本次扫描的候选缓存仅在所有校验通过后替换旧缓存。任一检查失败，缓存不更新，API/worker 继续按 v0.4.1 的隔离规则停止读写。业务事务回滚不会让未提交的业务状态变成下一次免检查的状态。

API 与两个 worker 各有自己的缓存。其他进程合法提交后，新行和变化的状态必须在当前进程重新验证。重启没有缓存，需要完整校验。缓存依赖进程内存和代码可信；不防持有签名密钥或控制进程的攻击者。

这仍不能独立识别整库回退到较早的合法快照；那需要受保护的外部检查点。调度元数据和去重列等原有未签名范围也没有因此自动获得保护，完整说明见 [审计故障处置](audit-integrity.md)。

## 缓存预算与开关

API、diagnose worker、observe worker 默认各使用 **16 MiB 估算留存预算**。预算根据 Python 元组、标量对象大小和索引开销保守计费。超出预算的记录继续完整验证；不会截断审计历史、跳过检查或无限扩张缓存。

可在每个进程启动参数中分别配置 `--audit-cache-mib 0..256`，单位 MiB。例如：

```powershell
python -m mttr_guard.enterprise api --config config/enterprise.local.json --db artifacts/enterprise.db --audit-cache-mib 16
python -m mttr_guard.enterprise worker --queue diagnose --config config/enterprise.local.json --db artifacts/enterprise.db --audit-cache-mib 16
python -m mttr_guard.enterprise worker --queue observe --config config/enterprise.local.json --db artifacts/enterprise.db --audit-cache-mib 16
```

设为 `0` 会关闭结果复用，继续执行全部密码学校验。该开关适合性能对照或排查；不用迁移数据库或换审计密钥。存储完整性失败后的恢复仍需按手册处理，关闭缓存不是恢复手段。

预算不是进程 RSS 上限。验证时旧缓存与候选索引会暂时共存（未变更条目共享），还需要 Python 运行时、SQLite、请求、状态集合等内存。三个进程的预算分别生效；容器内存限制要留余量。当前按扫描顺序保留能装入预算的条目，没有跨进程共享、分布式失效协议或磁盘缓存。

## 同机对照结果

2026-09-18，Windows 11 / Python 3.14.7，固定 enterprise 依赖；100 个合成事件，每档 10 个样本，单进程。先单独测一次冷扫描，再计时 `operational` 查询和访问审计追加，共两个受保护事务。先跑关闭缓存，再跑默认预算：

```powershell
python -m scripts.benchmark_audit_guard --records 1000 10000 25000 --samples 10 --cache-mib 0 --output artifacts/audit-uncached.json
python -m scripts.benchmark_audit_guard --records 1000 10000 25000 --samples 10 --cache-mib 16 --output artifacts/audit-cached.json
```

| 起始审计记录数 | 关闭缓存 P50 / P95 | 16 MiB 缓存 P50 / P95 | P50 比值 |
| --- | --- | --- | --- |
| 1,000 | 78.986 / 98.412 ms | 19.930 / 25.566 ms | 4.0 倍 |
| 10,000 | 438.220 / 474.983 ms | 97.361 / 109.391 ms | 4.5 倍 |
| 25,000 | 1,023.232 / 1,047.918 ms | 637.093 / 806.785 ms | 1.6 倍 |

1 万条记录时缓存估算留存为 10,647,470 字节；2.5 万条时为 16,777,042 字节，接近预算。后者最后一次校验有 16,376 次命中、8,833 次未命中（包含记录、事件和状态），未命中的部分继续完整计算。报告还输出预算及命中数，便于解释历史增长后的性能变化。

缓存有冷启动成本：1 万条记录的一次冷读取，关闭缓存为 208.948 ms，建立缓存为 289.769 ms。上表的收益属于热态，10 个样本的 P95 即最大观测值。这些数字不包含 HTTP、采集、模型、并发等待、真实故障或长时间运行，不能转换成生产 QPS 或 MTTR 改善率。

算法仍随历史规模线性扫描，且持有 SQLite 写锁。预算不足时收益下降；它没有解决多副本协调、历史归档、独立审计存储或高可用。扩大试点前仍需按预期历史规模与并发，在目标环境验证入库延迟和恢复窗口完整性。

## 验证

新增回归覆盖热缓存下的 body/scope/state/事件/签名/payload/前驱/链头/密钥改动、记录删除、额外事件、旧状态重放、另一实例提交、缓存预算耗尽、未留存记录篡改、失败后不发布新缓存、事务回滚，以及外部检查点不能被缓存绕过。还通过实际重建 SQLite 表改变时间字段的数值类型，确认即使 Python 相等比较成立也不能命中缓存。原有全部故障隔离测试继续执行。

真实 API 与两个 worker 的恢复/重启/备份/篡改隔离演练默认启用缓存；CI 在 Linux/Windows 和 Python 3.11/3.14 执行。实际结果见 [验证记录](validation.md)。
